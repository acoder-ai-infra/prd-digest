# PRD Digest

> 在 AI 开始写代码之前，先判断这个需求是否值得写。

PRD Digest 是一个用于**产品需求准入评审**的 AI Agent Skill。它接收一份 PRD 或一段需求描述，输出结构化的评审结论：需求类型、综合评分、评审置信度、逐维度判定、阻断项，以及 2～5 条可直接执行的关键行动。

本项目是纯 Markdown 规则集，不含运行时代码，也没有任何第三方依赖。

## 1. 它解决什么问题

AI 编码工具把实现成本压低了一个数量级之后，研发链路的瓶颈就从"写得快不快"移到了"要不要写"。而需求侧的工程化程度明显落后：

1. **文档厚度被当成需求成立度**。一份 40 页、图文完备的 PRD 往往比一页纸的需求更容易过评审，即使它的用户问题完全没有证据。
2. **文档声称被当成文档证明**。"用户强烈需要""预计大幅提升"这类措辞在评审中被直接接受，而背后可能只是撰写者的推断。
3. **评审标准依赖个人经验**。同一份 PRD 换个评审者、换个时间，结论可能相反；资深产品经理的判断力是隐性的，无法传给团队。
4. **评审结论无法执行**。大量评审以"再想想""方案不够清晰"结束，没说清缺什么、为什么缺、怎么补。
5. **Agent 会放大上游缺陷**。Agent 会忠实地把一个逻辑不成立的需求高速实现出来。上游一处未验证假设，下游变成成百上千行需要回滚的代码。

需求评审中稀缺的不是知识，而是**纪律**：把 PRD 拆干净、把证据分级、把没证据的地方老实标成"材料不足"、每次都用同一把尺子。人在会议压力和时间压力下很难稳定守住这些纪律，而这恰好是 AI 的强项。

因此本项目的做法是：把优秀评审者的隐性判断显性化为规则，交给 AI 稳定执行，并把 AI 严格限定为**克制的评审官**，而不是替人做决策的裁判。

## 2. 快速开始

### 2.1 安装

将本仓库放入你的 Agent 的 Skill 目录，例如：

```bash
git clone <repo-url> ~/.claude/skills/prd-digest
```

不同 Agent 的 Skill 目录不同（如 Claude Code、Qoder 等），请按对应产品文档放置。目录中必须保留 `SKILL.md` 与 `references/`。

### 2.2 使用

把需求材料交给 Agent，直接提出评审请求即可：

```
帮我评审一下这个需求：<粘贴 PRD 或需求描述>
```

默认输出精简摘要。需要完整报告时明确说明：

```
详细评审这份 PRD，展开逐项扣分依据、关键假设、MVP 优先级和指标体系
```

### 2.3 最低可评审输入

只要具备以下三项就能开始评审：

1. 需求要解决的问题；
2. 大致目标用户或使用对象；
3. 拟采用的产品方案。

材料不足时，Skill 不会虚构用户、数据或现有能力，而是继续完成暂定评审、降低评审置信度，并标出哪些判断依赖补充材料。

## 3. 输出示例

输入：在客服后台订单列表中，为订单号增加复制按钮；客服目前需手动选择文本；过去 30 天收到 18 次相关反馈；客服团队 42 人。

输出：

```markdown
# PRD 评审摘要

【需求类型】小型需求
【综合评分】86 / 100
【评审置信度】82 / 100
【总体结论】推荐立项
【阻断项】0 项
【一句话结论】问题、用户和方案明确，补充复制失败处理与简单埋点后即可实施。

| 方向 | 结果 | 证据 | 判定依据 |
|---|---|---|---|
| 1. 问题与价值 | 通过 | E3 | 依据：42 名客服存在高频复制场景，已有 30 天反馈；建议：补充日均次数以量化收益。 |
| 2. 方案闭环 | 有条件通过 | E3 | 依据：点击复制和成功提示路径完整；扣分：未说明权限异常和空值；建议：补充失败提示。 |
| 3. 体验与信任 | 通过 | E2 | 依据：操作符合现有心智，不增加学习成本；建议：保持提示样式一致。 |
| 4. 范围与复用 | 有条件通过 | E2 | 依据：范围仅限客服后台；扣分：未说明是否复用已有复制组件；建议：沿用统一组件和埋点。 |
| 5. 验证与可逆性 | 通过 | E2 | 依据：可用成功率和使用人数验证，功能容易关闭；建议：上线两周后复盘。 |

【关键行动】
1. 补充复制失败、权限异常和空值处理
2. 复用现有复制组件并增加成功率埋点
```

完整示例见 [`examples/`](examples/)。

## 4. 核心机制

### 4.1 分级评审

需求规模由影响面、流程变化、业务重要性、不确定性、规则复杂度和发布风险决定，**不由文档页数决定**。Skill 先对八个分类因素各评 0～2 分，再判定需求类型：

| 分类总分 | 需求类型 | 评审模板 |
|---:|---|---|
| 0～5 | small | 小型需求 5 维 |
| 6～10 | medium | 大中型需求 7 维 |
| 11～16 | large | 大中型需求 7 维 + 更严格的证据与阻断要求 |

另有强制升级条件（如新增付费机制、改造核心路径、依赖未验证的关键用户行为）与降级条件。分类不确定时一律采用更严格的模板。

### 4.2 评审维度与权重

大中型需求 7 维：

| 维度 | 权重 |
|---|---:|
| 需求成立度 | 18 |
| 价值与影响 | 16 |
| 方案适配与业务闭环 | 18 |
| 体验与信任 | 12 |
| 范围与复杂度控制 | 12 |
| 能力复用与产品杠杆 | 10 |
| 验证与可逆性 | 14 |

小型需求 5 维：问题与价值 25、方案闭环 25、体验与信任 15、范围与复用 20、验证与可逆性 15。

每个维度给 0～5 原始分，按 `原始分 ÷ 5 × 权重` 加权求和得到综合评分。

### 4.3 证据等级设定评分上限

证据不是一个并列的评分项，而是**横向机制**，用于限制"需求成立度""价值与影响""预期效果"这类判断的最高分，从而避免同一个"证据不足"在多个维度里被重复扣分：

| 等级 | 含义 | 最高原始分 |
|---|---|---:|
| E0 | 无证据，只有结论 | 2 / 5 |
| E1 | 主观判断、单点反馈、竞品有该功能 | 3 / 5 |
| E2 | 多个相似反馈、少量访谈、间接数据 | 4 / 5 |
| E3 | 有样本与口径的结构化数据、系统访谈 | 4.5 / 5 |
| E4 | 实验、灰度、原型测试、长期稳定数据 | 5 / 5 |

### 4.4 阻断项守住底线

综合评分先得到基础评级，再应用阻断项的评级上限。**高分不能抵消阻断项**：

| 综合评分 | 基础评级 |
|---:|---|
| 85～100 | 推荐立项 |
| 75～84.9 | 有条件推进 |
| 60～74.9 | 建议修改后复评 |
| 40～59.9 | 建议重新定义 |
| 0～39.9 | 不建议立项 |

九类阻断项：G1 无法识别核心用户或用户任务、G2 问题与方案明显错位、G3 缺少目标结果、G4 缺少范围边界、G5 致命假设无证据且无验证计划、G6 关键业务规则自相矛盾、G7 核心复用假设未确认且失败会显著改变范围、G8 高影响需求缺少关闭与恢复策略、G9 明显合规、欺骗、隐私或用户伤害风险。存在多个阻断项时取最严格上限。

### 4.5 评审置信度独立计算

置信度不并入综合评分，按输入完整度 C、证据质量 E、内部一致性 I 计算：

`评审置信度 = ((0.4 × C) + (0.4 × E) + (0.2 × I)) ÷ 5 × 100`

这样可以区分两件常被混淆的事：**需求质量低**和**材料不足**。

### 4.6 方法论来源

Skill 吸收以下方法论的底层原则，但不按方法论名称机械打分：JTBD（用户、情境、任务、替代方案）、RICE（Reach、Impact、Confidence）、Assumption Mapping（事实、推断、假设、验证优先级）、MoSCoW（范围与本期不做项）、HEART（采用、任务成功、留存、参与、满意度）。映射关系见 [`references/methodology-map.md`](references/methodology-map.md)。

## 5. 能力边界

明确边界是本项目的设计目标之一。Skill 默认**不**输出以下结论，而是在触发时给出对应的专项评审建议：

| 不承担 | 处理方式 |
|---|---|
| 服务拆分、数据库设计、性能容量、技术回滚、工作量估算 | 触发技术方案评审 |
| 像素级视觉、设计系统审查、WCAG 审计、可用性测试 | 触发 UX Review |
| 市场规模、定价、获客成本、ROI 等完整 Business Case | 触发商业论证评审 |
| 法务、安全、隐私、行业合规的专业结论 | 触发专项评审 |
| 替代真实用户研究与线上实验 | 给出低成本验证建议 |

没有原型时，Skill 可以评价用户任务流程、操作摩擦、用户控制权、自动化透明度和恢复路径，但不评价视觉层级、字体颜色间距、控件精致度和微交互。

**重要**：本项目输出的是结构化判断，不是立项裁决。评分用于横向比较与问题定位，不代表数学意义上的真实价值。请勿把评分当作决策依据的唯一来源。

## 6. 目录结构

```
prd-digest/
├── SKILL.md                              # 主规则：目标、流程、约束、自检清单
├── references/
│   ├── demand-classification.md          # 需求分类：八因素、升降级条件
│   ├── scoring-rubric.md                 # 评分细则：7 维 / 5 维逐档标准与权重
│   ├── evidence-and-gates.md             # 证据等级、假设类型、阻断项、评级
│   ├── capability-reuse.md               # 能力复用：直接 / 扩展 / 新增 / 不复用
│   ├── review-boundaries.md              # 能力边界与专项评审触发
│   ├── output-template.md                # 默认摘要模板
│   ├── output-template-detailed.md       # 详细报告模板
│   └── methodology-map.md                # 方法论到评审维度的映射
└── examples/
    ├── small-review-example.md           # 小型需求评审示例
    └── large-review-example.md           # 大中型需求评审示例
```

`examples/` 仅用于校准评分尺度与表达方式，不能覆盖正式规则。

## 7. 适用场景

适用于新产品与新业务能力、核心流程改版、商业化与增长需求、To B 与内部平台需求、已有功能的小范围优化、PRD 初审与复审、立项前评估，以及 Agentic Coding 之前的需求准入。

## 8. 贡献

本项目是规则资产，欢迎通过 Issue 与 Pull Request 参与改进。提交规则变更时请一并说明：

1. 改动影响哪个维度或哪条机制；
2. 为什么现有规则会给出错误判断，最好附上一个真实（可脱敏）的需求样本；
3. 是否会改变已有示例的评分尺度。

评分尺度的稳定性比新增规则更重要。任何会导致同一份需求评分显著漂移的改动，需要同步更新 `examples/` 中的校准示例。
