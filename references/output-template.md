# 默认结构化摘要模板

## 1. 输出原则

- 结论先行；
- 大中型需求输出 7 个维度；
- 小型需求输出 5 个维度；
- 每个维度同时给出结果、证据和判定依据；
- 使用普通阿拉伯数字编号，例如 `1. `；
- 禁止使用带圈数字；
- 不复述整份 PRD；
- 不输出无依据技术或 UI 结论；
- 用户指定格式时，以用户格式为准。

## 2. 总体评级

| 综合评分 | 基础评级 |
|---:|---|
| 85～100 | 推荐立项 |
| 75～84.9 | 有条件推进 |
| 60～74.9 | 建议修改后复评 |
| 40～59.9 | 建议重新定义 |
| 0～39.9 | 不建议立项 |

阻断项可以限制最终评级，但不修改综合评分。

## 3. 大中型需求默认模板

```markdown

【需求类型】中型需求 / 大型需求

【阻断项】{0 / X} 项
【一句话结论】{用一到两句话说明价值、主要问题和是否可以推进}

| 方向 | 结果 | 证据 | 判定依据 |
|---|---|---|---|
| 1. 需求成立度 | {通过 / 有条件通过 / 不通过 / 材料不足 / 不适用} | {E0～E4 / —} | 依据：...；扣分或阻断：...；建议：... |
| 2. 价值与影响 | ... | ... | ... |
| 3. 方案适配与业务闭环 | ... | ... | ... |
| 4. 体验与信任 | ... | ... | ... |
| 5. 范围与复杂度控制 | ... | ... | ... |
| 6. 能力复用与产品杠杆 | ... | ... | ... |
| 7. 验证与可逆性 | ... | ... | ... |

【致命假设】{0 / X} 项
1. {仅列最重要的 0～3 项；没有则写“无”}

```

## 5. 判定依据写法

优先使用：

`依据：正向事实；扣分：当前不足；建议：下一步动作。`

存在阻断项时使用：

`依据：正向事实；阻断：不能进入下一阶段的问题；建议：解除阻断所需动作。`

材料不足时使用：

`材料不足：缺少什么；影响：无法判断什么；建议：补充什么。`

每一行尽量控制在 80～180 个中文字符内。

## 6. 长度控制

- 大中型需求默认约 700～1500 字；
- 小型需求默认约 300～800 字；
- 每项只保留最关键的依据、扣分和动作；
- 详细事实、假设矩阵、MoSCoW 和指标表放入详细模式。

## 7. 大中型示例

```markdown
# PRD 评审摘要

【需求类型】大型需求
【综合评分】61 / 100
【评审置信度】58 / 100
【总体结论】建议修改后复评
【阻断项】2 项
【一句话结论】商家内容生产问题基本成立，但当前方案同时跨越生成、自动发布和收费等多个未验证假设，首版范围过大。

| 方向 | 结果 | 证据 | 判定依据 |
|---|---|---|---|
| 1. 需求成立度 | 有条件通过 | E2 | 依据：访谈显示部分商家存在内容制作耗时；扣分：样本较少，缺少频率和耗时基线；建议：补充结构化数据。 |
| 2. 价值与影响 | 有条件通过 | E1 | 依据：降低内容成本可能提升商家活跃；扣分：覆盖量级和收入链路未证明；建议：量化目标商家与节省时间。 |
| 3. 方案适配与业务闭环 | 有条件通过 | E2 | 依据：文案生成与任务匹配；阻断：自动发布与已证明问题之间跨度过大；建议：先保留生成、编辑和手动发布。 |
| 4. 体验与信任 | 不通过 | E0 | 阻断：自动发布缺少确认、撤销和责任边界；建议：增加人工确认和错误恢复。 |
| 5. 范围与复杂度控制 | 不通过 | — | 阻断：首版同时验证生成、选品、发布、分析和付费；建议：收敛为单一生成采用闭环。 |
| 6. 能力复用与产品杠杆 | 材料不足 | E0 | 材料不足：未说明商品、审核和渠道发布能力；建议：补充直接复用、扩展复用和新增清单。 |
| 7. 验证与可逆性 | 不通过 | E1 | 阻断：无灰度、护栏和停止标准；建议：定义采用率、修改幅度及关闭策略。 |

【致命假设】3 项
1. 商家愿意采用 AI 生成内容
2. 商家愿意授权系统自动发布
3. 商家愿意为该能力付费

【关键行动】
1. 将 V1 收敛为“生成、编辑、手动发布”闭环
2. 验证内容采用率和持续使用意愿
3. 补充现有商品、审核和发布能力复用边界
```

## 8. 小型示例

```markdown
# PRD 评审摘要

【需求类型】小型需求
【综合评分】86 / 100
【评审置信度】82 / 100
【总体结论】推荐立项
【阻断项】0 项
【一句话结论】问题、用户和方案明确，补充复制失败处理与简单埋点后即可实施。

| 方向 | 结果 | 证据 | 判定依据 |
|---|---|---|---|
| 1. 问题与价值 | 通过 | E3 | 依据：42 名客服存在高频复制场景，已有 30 天反馈；建议：补充日均次数以量化收益。 |
| 2. 方案闭环 | 有条件通过 | E3 | 依据：点击复制和成功提示路径完整；扣分：未说明权限异常和空值；建议：补充失败提示。 |
| 3. 体验与信任 | 通过 | E2 | 依据：操作符合现有心智，不增加学习成本；建议：保持提示样式一致。 |
| 4. 范围与复用 | 有条件通过 | E2 | 依据：范围仅限客服后台；扣分：未说明是否复用已有复制组件；建议：沿用统一组件和埋点。 |
| 5. 验证与可逆性 | 通过 | E2 | 依据：可用成功率和使用人数验证，功能容易关闭；建议：上线两周后复盘。 |

【关键行动】
1. 补充复制失败、权限异常和空值处理
2. 复用现有复制组件并增加成功率埋点
```

## 9. 禁止输出

- 带圈数字或其他装饰性编号；
- 只有一个总分而没有依据；
- 把证据单独作为重复评分维度；
- 无材料时猜测现有能力、UI 或技术实现；
- 把“复用越多”直接等同于更高分；
- 完整技术架构、研发工作量或法律结论；
- 方法论术语堆砌。
